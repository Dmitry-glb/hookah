## 1. Краткое описание проекта

DimHookah — статическое **PWA для кальяна** без сервера и регистрации. Основные сценарии:

1. Выбрать случайный вкус табака в рулетке по реальному каталогу HTReviews.
2. Отфильтровать каталог по бренду, крепости, вкусовому направлению и рейтингу.
3. Сохранить вкус в личную коллекцию («Хочу покурить» / «Уже попробовал»).
4. Запустить прогрев, вести таймер покура, записать чашу, табак, угли, стоимость и оценку.
5. Смотреть историю, статистику, бюджет и склад углей.
6. Перенести вкус из коллекции сразу в забивку кнопкой «В чашу».

Приложение работает как обычная веб-страница и как установленная PWA. Все пользовательские данные хранятся локально: `localStorage` + IndexedDB. Внешний сервис только один — публичный сайт/API HTReviews (каталог и изображения).

## 2. Архитектура и структура

### 2.1. Тип приложения

- **Vanilla HTML/CSS/JavaScript**, без фреймворка, сборщика и транспиляции.
- Два независимых классических скрипта:
  - `app.js` — глобальные функции, обработчики `onclick`, трекер, история, таймеры, экспорт/импорт.
  - `catalog-ui.js` — IIFE, вкладки, фильтры, рулетка, коллекция, действия.
- Чистая логика вынесена в UMD-подобный `lib/catalog-core.js`; в браузере она доступна как `window.DimHookahCore`.
- `lib/htreviews.js` и `scraper.js` — только Node.js, в браузер не загружаются.
- CSS разделён на два слоя:
  - `style.css` — базовая тема и старые компоненты трекера;
  - `ui.css` — новый интерфейс, адаптивность, рулетка, коллекция, переопределения.
- `index.html` подключает скрипты в порядке: `lib/catalog-core.js` → `app.js` → `catalog-ui.js`.

### 2.3. Потоки данных

**Каталог и рулетка:**

```text
flavors.json
  → fetch('flavors.json') в catalog-ui.js
  → Core.normalizeCatalog()
  → state.catalog / state.bySlug / state.stats
  → Core.filterItems() по state.filters
  → Core.pickRandomItem()
  → buildReel() + positionReel()
  → renderResult()
```

**Сессия и история:**

```text
app.js DOMContentLoaded
  → initCatalogs() (чаши, бренды, пачки, угли)
  → restoreActiveSessionIfAny()
  → открытие IndexedDB HookahDB
  → loadAllData()
  → renderData(sessions)
  → applySessionDefaultsFromLast()
  → история + аналитика + бюджет
```

**Связь двух скриптов через события:**

- `catalog-ui.js` после загрузки каталога отправляет `dimhookah:catalog-ready` с `detail.catalog`.
- `app.js` слушает это событие и заполняет бренды/вкусы формы сессии через `applyCatalogToSession()`.
- `app.js` при отрисовке истории отправляет `dimhookah:history-ready`; `catalog-ui.js` перерисовывает бейджи результата «уже в истории».
- `app.js` предоставляет глобальную `fillSessionFromCollection(data)`; `catalog-ui.js` вызывает её по кнопке «В чашу».

## 5. Важные технические решения и причины

1. **Vanilla JS вместо фреймворка.** Проект должен быть статическим, без сборки и бэкенда; GitHub Pages достаточно.
2. **`lib/catalog-core.js` как чистый модуль.** Позволяет тестировать фильтры/выбор/коллекцию в Node и использовать те же функции в браузере.
3. **Каталог как снимок `flavors.json`.** Приложение не зависит от доступности HTReviews при обычном запуске; обновление — отдельный CLI.
4. **Каталог ограничен топ-60 брендами.** Пользователь явно попросил только бренды из топа, а не все 301 бренд HTReviews. Плюс `musthave`.
5. **Только выпускаемые и лимитированные статусы.** `normalizeFlavor` по умолчанию исключает `status_id=4` (снят), `3` (не известен) и `5` (шуточный); `--include-discontinued` фактически включает и 3/5 (см. риски).
6. **Нормализация терпима к старым данным.** `normalizeCatalogItem` поддерживает старые `tags`-строки и отсутствующие `taste_groups`.
7. **Двойное хранение сессий.** `saveSessionsToStorage` пишет в `localStorage` и IndexedDB; `loadAllData` выбирает более длинный массив. Это даёт миграцию/fallback, но создаёт риск рассинхронизации.
8. **PWA-стратегии.** HTML/JS/CSS — network-first с офлайн-фолбэком; `flavors.json` — stale-while-revalidate; изображения/иконки — cache-first. Причина: старый cache-first для `app.js` не доставлял новые функции в установленную PWA.
9. **Service worker v16 и принудительный reload.** При наличии старого кеша SW после `claim()` перезагружает окна; `app.js` дополнительно слушает `controllerchange`. Причина: старые версии не умели обновляться сами.
10. **Динамические манифесты и иконки.** `updateThemeAssets()` переключает `manifest.json` / `manifest-light.json`, favicon, `apple-touch-icon` и логотип. Причина: одна тема должна получать свою иконку.
11. **Локальные уведомления вместо push-сервера.** `setTimeout` + `ServiceWorkerRegistration.showNotification` + звук через `<audio>`/WebAudio; серверного push нет.
12. **История с клиентской пагинацией.** Фильтрация и поиск идут по всему массиву, затем показываются первые 5; это сохраняет поиск старых записей.
13. **Дефолты из последней сессии.** `getLatestSession` выбирает максимальный `id`; копируются чаша, бренд/вкус, угли, расстановка и время прогрева, но не граммовка.

## 6. История существенных ошибок и экспериментов

### 6.1. HTReviews: HTML-пагинация не работает

- **Проблема:** нужно получить все вкусы бренда, а не только первые 20.
- **Пробовали:** HTML-страницу `/tobaccos/<slug>` с параметром `?o=` и пагинацией.
- **Результат:** страница всегда отдавала первые 20, хотя `data-count` был больше.
- **Причина:** сайт не применяет offset к HTML-списку так, как ожидалось.
- **Вывод:** использовать API `POST /postData` с `action: objectByBrand`, `limit`, `offset`, `sort`; `GET /getData?action=brands` — для рейтинга.
- **Не повторять:** скрейпинг HTML-списка для пагинации.

### 6.2. Неполный список брендов

- **Проблема:** в `flavors.json` было 41 бренд, Black Burn отсутствовал.
- **Проверили:** `action=brands&r=position` отдаёт 60 брендов; `r=others` — ещё 241 бренд. Всего 301.
- **Результат:** 260 брендов отсутствовали; Black Burn был в топ-60.
- **Решение пользователя:** оставить только топ-60 и выпускаемые вкусы.
- **Итог:** 56 брендов с активными вкусами, 4 бренда без активных вкусов (Smoke Angels, Leteam, Cobra, Aircraft) не попали в JSON.
- **Не повторять:** считать, что топ-60 = все бренды сайта; и что 60 брендов всегда дадут 60 записей.

### 6.3. Статусы и MUSTHAVE

- **Проблема:** на странице MUSTHAVE заявлено 104 вкуса, API отдавал 91, а в каталог попадало 87.
- **Причина:** 4 снятых с производства; 13 позиций сайт не отдаёт ни в списке, ни в API, ни в поиске.
- **Решение:** в JSON только `Выпускается` + `Лимитированный`; 87 MUSTHAVE.
- **Не повторять:** ожидать 104 или 91 активных вкуса из API.

### 6.4. PowerShell испортил UTF-8 файл

- **Проблема:** после `Get-Content`/`Set-Content` в `catalog-ui.js` появились mojibake, BOM и потерянные символы.
- **Причина:** перезапись UTF-8 через PowerShell с неверной кодировкой.
- **Решение:** восстановление через `iconv-lite` cp1251→UTF-8 и ручные правки; проверка на `U+FFFD`/BOM.
- **Не повторять:** переписывать UTF-8 файлы проекта через `Get-Content`/`Set-Content`. Использовать `edit`/`write` или Node/Python с явным UTF-8.

### 6.5. Playwright и `spawn EPERM`

- **Проблема:** в ограниченной Windows-песочнице Playwright не запускал Chrome, `spawn EPERM`.
- **Решение:** E2E запускать в окружении с полным доступом; текущий runtime это позволяет.
- **Не повторять:** пытаться запускать browser E2E в read-only/workspace-write sandbox без проверки.

### 6.6. PWA не получала новые функции

- **Проблема:** в веб-версии новые функции были, в установленной PWA — нет.
- **Причина (подтверждена кодом):** service worker v14 отдавал `app.js`/CSS по cache-first; `sw.js` не менялся, новый SW не устанавливался, PWA продолжала использовать старый `app.js`.
- **Решение:** v15/v16, network-first для HTML/JS/CSS, `updateViaCache: 'none'`, `registration.update()`, reload по `controllerchange`, принудительный navigate клиентов при старом кеше.
- **Проверено:** live `sw.js` v16; E2E видит активный SW и cache v16.
- **Не повторять:** менять `app.js`/CSS без поднятия `CACHE_NAME`, если SW-стратегия снова станет cache-first.

### 6.7. E2E ждал скрытый элемент как видимый

- **Проблема:** `page.waitForSelector('#active-session.hidden')` по умолчанию ждал `visible`, хотя элемент скрыт.
- **Решение:** `{ state: 'attached' }`.
- **Вывод:** для скрытых состояний явно указывать `state`.

### 6.8. Дубликат бренда из-за похожих символов

- **Проблема:** в селекте появились визуально одинаковые `Наш` и `Nаш`.
- **Причина:** старое значение по умолчанию и каталожное имя с латинской `N`; `getBrandOptionsHtml` добавлял legacy-опцию.
- **Решение:** `isLegacyDefaultBrand` и выбор каталожного бренда вместо legacy-дубликата; E2E проверяет алфавит.
- **Не повторять:** бездумно добавлять произвольный `selectedVal` в options без проверки на каталожный аналог.

### 6.9. Иконка установленной PWA

- **Проблема:** нужно менять иконку PWA при смене темы.
- **Что сделано:** два манифеста, динамический `<link rel="manifest">`, favicon, apple-touch-icon, логотип.
- **Ограничение:** iOS кеширует иконку домашнего экрана; после установки она не меняется автоматически и требует удаления/повторного добавления. Android/WebAPK может подхватить манифест при обновлении, но это не гарантировано.
- **Не считать доказанным:** смену иконки уже установленной PWA на реальном iOS/Android без ручной проверки.

### 6.10. Фоновые уведомления

- **Проблема:** звук/уведомление появлялись только при открытии приложения.
- **Что сделано:** отдельные `setTimeout` на момент готовности чаши и на 60/90 минут покура, `sendPush` через Service Worker, `mediaSession.playbackState='playing'`, keep-alive audio, очистка после сессии.
- **Ограничение:** веб-приложение не может гарантировать доставку, если ОС полностью выгрузила PWA; для гарантии нужен серверный Web Push. На iOS фоновые веб-уведомления ограничены.
- **Не считать доказанным:** реальную доставку в фоне на Android/iOS без отдельного device-теста.

### 6.11. Неудачные/незавершённые эксперименты

- **Дизайн-концепт премиального редизайна** обсуждался отдельно; был собран временный макет вне проекта, но в приложение он не внедрялся. Текущий UI — существующий тёмный интерфейс, а не премиальный gold-концепт.

- **4 бренда без выпускаемых вкусов** не добавлялись; вопрос, показывать ли их пустыми, остаётся открытым.

## 8. Известные проблемы и ограничения

### 8.1. Данные каталога

- В каталоге **56 брендов**, а не 60: у Smoke Angels, Leteam, Cobra, Aircraft на HTReviews нет ни одного выпускаемого вкуса.
- 241 бренд из вкладки «Все остальные» не включён по решению пользователя.
- 13 позиций MUSTHAVE недоступны через публичный API.
- `flavors.json` — 5.48 МБ; первая загрузка/парсинг на слабом мобильном может быть заметной.
- `icon_dark.png` — 2.1 МБ и не используется в манифесте; возможен лишний вес репозитория.

### 8.2. PWA

- Иконка уже установленной PWA на iOS не меняется автоматически.
- Нет гарантии фоновой доставки уведомлений при выгрузке приложения ОС; серверного push нет.
- `client.navigate()` при обновлении SW перезагружает открытые окна; активная сессия восстанавливается из `hookah_active_session`, но несохранённые изменения за последние ~250 мс могут потеряться.
- Real offline behavior (полный refresh без сети) не проверялся E2E.
- `SHELL_ASSETS` не включает 1024-иконки; они не нужны для PWA, но лежат в репозитории.

### 8.3. Хранение данных

- Двойная запись в localStorage и IndexedDB.
- `loadAllData` выбирает массив с большей длиной (`dbData.length >= localData.length`), а не более новый по времени. При равной длине возможна потеря более новых локальных данных.
- `saveSessionsToStorage` делает `clear()` + `put()` без обработки ошибок транзакции; при сбое IndexedDB остаётся localStorage.
- Все данные привязаны к браузеру/профилю; синхронизации между устройствами нет.

### 8.4. UI/код

- После добавления второго табака форма остаётся в режиме микса; отдельного возврата к соло нет. Удаление последней строки блокируется.
- В `index.html` остался `brand-manager-modal`, а в `app.js` — функции управления брендами, хотя кнопки открытия удалены. Это мёртвый код/скрытый UI.
- `style.css` и `ui.css` частично дублируют/переопределяют друг друга; без визуальной проверки легко сломать тему.
- `DEFAULT_BRANDS` содержит legacy-алиасы (`Musthave`, `Наш`, `Blackburn`), которые не совпадают с каталожными именами; специальная логика `isLegacyDefaultBrand` компенсирует это.
- История/даты в `docs/` — тестовые.

### 8.5. Тесты

- Нет тестов:
  - реальной фоновой доставки уведомлений/звука;
  - установленной PWA и смены иконки на iOS/Android;
  - обновления PWA со старого кеша на реальном устройстве;
  - офлайн-загрузки;
  - экспорта/импорта JSON и Apple Notes;
  - сохранения/редактирования ручной сессии;
  - точных формул статистики/бюджета/углей;
  - accessibility и производительности.
- E2E seeds 7 синтетических сессий в `localStorage`, поэтому не проверяет реальную миграцию старых данных пользователя.
- E2E требует Chrome и иногда полного доступа к процессам (в песочнице был `spawn EPERM`).

### 8.6. Внешние зависимости

- HTReviews может менять API/разметку/статусы.
- Изображения загружаются с `htreviews.org`; без сети/при блокировке будут заглушки.
- Нет контроля версий API и нет fallback-сервера.

## 9. Требования пользователя и запреты

### 9.1. Явные требования (подтверждены историей)

- Мобильный Android: вертикальный скролл, без зума и горизонтального скролла.
